# 2026-08-20 — 0.2.6: the focus-loss freeze is fixed

**TL;DR:** the worst headset-session caveat — *"keep the game window focused
or frames stop"* — is root-caused and fixed. XIII.exe polls
`GetForegroundWindow()` in its main loop and stops ticking the engine when
any other window is foreground; the proxy now lies to exactly that poll.
Desk-verified with a scripted focus steal; staged for headset confirmation.

## The investigation (live debugging, x32dbg)

1. **Reproduced with telemetry:** stole focus with a scripted `notepad`
   launch while `[xiii-perf]` heartbeats streamed. Heartbeats stopped dead
   within a second of the steal — `Present` was never called again, and the
   process sat at exactly flat CPU, so the whole loop was blocked, not just
   skipping draws.
2. **Caught it in the act:** ran the game under x32dbg, stole focus at
   steady state, broke in. The main thread was parked inside
   `kernel32!Sleep(8)` under Core.dll's `appSleep(float)` (recognizable
   fld/fmul-by-1000/ftol/Sleep pattern), called from XIII.exe's main loop.
3. **Read the loop:** XIII.exe (a UE `CMainLoop` shape: `GIsRunning` /
   `GIsRequestingExit` globals, tick-rate limiter with
   `Engine->GetMaxTickRate()`) checks every iteration:
   `GetForegroundWindow` → owning thread == main thread, and
   `!IsIconic(foreground)`. On failure it flags inactive, calls the engine's
   deactivate path (which also mutes audio), skips `Engine->Tick`, and the
   tick-rate limiter degenerates into an 8 ms sleep-poll loop. No ini
   setting is consulted anywhere in that path.

## The fix

`proxy/focus_hook.cpp` IAT-hooks `user32!GetForegroundWindow` **in XIII.exe
only**. When the real foreground window belongs to another process, the hook
reports the game's device window (recorded by the CreateDevice/Reset hooks)
instead; when the game really is foreground, or no device window exists yet,
it tells the truth. The choose-what-to-report logic is a pure function in
`capture_core/focus_policy` with its own doctest suite (fifth in the
project), written test-first.

Scoping the hook to the EXE's import table is the point: WinDrv and Engine
keep their honest view of focus, so mouse capture and `WM_KILLFOCUS`
handling behave exactly as before. Two consequences worth knowing:

- Audio keeps playing while unfocused (mute-on-deactivate sits on the same
  branch as the pause) — intended for VR use.
- A *minimized* window still pauses, because the main loop `IsIconic()`s the
  window we report, and we report the game's own window. Deliberate
  minimize = deliberate pause seems right.

Gating: `[VR] KeepRenderingUnfocused` (default on), and the hook is only
installed when a VR host is enabled — with VR off, the stock game path is
untouched.

## Verification

Same scripted focus steal as the repro: heartbeats now continue at full rate
through 25 s of a foreign window holding focus (previously: dead within a
second). All 5 unit-test suites green. Game install restored to stock
afterwards (DLL MD5-verified, ini reverted).
